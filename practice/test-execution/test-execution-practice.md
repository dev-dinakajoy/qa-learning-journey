# Test Execution & Documentation Practice

## What I Practiced

I practiced executing test cases and documenting the results.

### 1. Test Case Execution

I executed test cases and recorded:

* Actual result
* Test status
* Execution notes

I used the following statuses:

* **Pass** — Actual result matches the expected result.
* **Fail** — Actual result does not match the expected result.
* **Blocked** — The test could not be executed because of a blocker.
* **Not Run** — The test has not been executed yet.

### 2. Bug Reporting

For failed test cases, I practiced creating bug reports with:

* Bug ID
* Bug title
* Description
* Steps to reproduce
* Expected result
* Actual result
* Severity
* Priority
* Environment

The goal was to make each bug report clear enough for a developer to reproduce and investigate the issue.

### 3. Test Scenarios

I practiced creating high-level test scenarios before writing detailed test cases.

**Example — Login**

* Verify that a registered user can log in with valid credentials.
* Verify email validation during login.
* Verify password validation during login.
* Verify login with invalid credentials.

### 4. Requirements Traceability Matrix

I practiced linking requirements to test cases and bugs.

This helped me understand how an RTM can be used to track whether requirements have been covered by testing and whether defects are associated with specific requirements.

### 5. Test Summary

I practiced summarizing test execution using metrics such as:

* Total test cases
* Executed test cases
* Passed
* Failed
* Blocked
* Not Run
* Test coverage
* Pass rate
* Fail rate

## What I Learned

I learned that QA documentation is not just about writing test cases.

A complete testing process involves:

**Requirements → Test Scenarios → Test Cases → Test Execution → Bug Reports → Test Summary**

Good documentation makes it easier to understand **what was tested, what happened, what failed, and what still needs attention**.
